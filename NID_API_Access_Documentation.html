1. Full Application Flow with NID Verification + System Security + Data Security + Data Privacy

1.1 System Overview

The BRTC Training Management System (TMS) is a full-stack web platform that digitizes the complete training lifecycle of 27 BRTC training centres in Bangladesh — from circular publication and public trainee registration to enrollment, attendance, assessment, certification and job placement. This document describes the application flow that touches the National ID (NID) data, the security controls at both the Network and Application layers, and the privacy measures applied to citizen data.

1.6 Data Privacy

  • Data Minimization: Only the fields required for a training admission are collected — NID, name, father/mother name, date of birth, address, phone. No unnecessary demographic or biometric data is stored.
  • Purpose Limitation: NID data is used strictly for (a) applicant identity verification, (b) duplicate-application prevention, and (c) age eligibility (minimum 21 years).
  • Role-Based Visibility: Citizen data is visible only to the citizen and to authorized staff of the relevant center / head office. Center admins are hard-isolated to their own center's data.
  • Access Accountability: Every NID read is recorded in the NID Access Log with the user, NID, timestamp, IP address and result — providing a complete audit trail for data-privacy enquiries (Section 3).
  • Consent & Transparency: Registration requires explicit user action (OTP verification); the application form is reviewed by the applicant before submission; submitted data can be inspected by the applicant through the trainee portal.
  • Retention & Deletion: Application data is retained for the training lifecycle and administrative accountability. Specific retention/deletion schedules can be configured in consultation with the data controller.
  • No External Sharing: NID data is not shared with third parties outside the BRTC administrative scope. Any NID API integration will be governed by a written data-processing agreement.

3. Admin Panel — NID Access Log Search Mechanism

To satisfy the requirement for a search mechanism on the Admin Panel for NID Access Logs — from which ID, when, IP trace, user name, address & mobile — the system now captures every NID read/write and exposes it through three search surfaces: the Django admin, the Head Office web panel, and the REST API.

3.2 Django Admin Search

Registered as a read-only model in the Django admin (NIDAccessLogAdmin):

  • Search fields: NID, target name, requester name, requester phone, IP address, user agent, message.
  • Filters: action (check/verify/apply), result (success/failed), created date.
  • Date hierarchy: drill-down by year → month → day.
  • Read-only: no add/edit/delete of audit records (immutable evidence).

3.3 Head Office Panel Search (Web UI)

A dedicated page System → “NID Access Log” (/ho/system/nid-access-logs) in the Head Office React panel provides:

  • A free-text search box across NID / name / phone / IP / user agent.
  • Action filter (NID check, NID verify, apply) and result filter (success / failed).
  • A paginated table showing ID, action, NID, target name, requester name/phone, IP address, result and timestamp.
  • Search results update in real time; pages of 25 records.

3.4 REST API Endpoint

For programmatic integration / report exports, a read-only endpoint is exposed (Head Office access only):

4. Developer-Side Backdoor & Code Breach Analysis

4.1 What Is a Backdoor?

A backdoor is any deliberate or accidental mechanism in software that allows an attacker — or a developer with knowledge of the code — to bypass normal authentication/authorization and gain unauthorized access to data or functionality. This section explains the realistic developer-side vectors, how the BRTC TMS codebase addresses them, and what an independent auditor should verify.

4.2 Common Backdoor Vectors in Web Applications

VectorDescription & Risk
Hardcoded credentialsUsernames/passwords/API keys compiled into source code allow anyone with repo access to authenticate.
Hidden / undocumented endpointsDev-only routes (admin panels, debug views, test hooks) accidentally left active in production.
DEBUG / verbose modes in productionDjango DEBUG exposes stack traces, settings, and the full source paths — an information-leak backdoor.
Weak / default passwordsDefault accounts (e.g. admin123, center@123) that are never changed.
Bypassed permission checksViews or actions (especially custom actions) that skip permission_classes, enabling IDOR/privilege escalation.
Secret key / JWT exposureIf the Django SECRET_KEY or JWT signing key leaks, tokens and session cookies can be forged.
Management / maintenance commandsServer-side scripts (e.g. account-recovery commands) that, if reachable, can recreate admin accounts.
Exposed infrastructure portsDatabase or cache ports open to the network (common in dev docker-compose) allow direct data access.
Unsanitized serialization / import hooksDangerous eval/exec/pickle or misconfigured template rendering could enable code execution.
Log/error leakageVerbose logs or stack traces that reveal file paths, DB names, or internal endpoints.

Findings that are not backdoors but require deployment discipline

  • Documented default credentials — must be changed on first login (enforce password rotation during go-live).
  • Dev-only exposed ports in docker-compose.yml — production compose does not expose them; do not reuse dev compose on the server.
  • JWT in localStorage — an XSS-resilience improvement (HttpOnly cookies) is recommended as defense-in-depth, not an active backdoor.

4.4 Recommended Audit Checklist

To independently confirm the absence of backdoors, the NID API provider / security team may perform the following checks on the delivered source:

  1. Search the repository for plaintext secrets: grep -rEi "(password|secret|api[_-]?key|token|BEGIN.*PRIVATE)" --exclude-dir=node_modules (excluding .env.example placeholders).
  2. Confirm DEBUG = False and ALLOWED_HOSTS are enforced from environment variables in production settings.
  3. Verify no unauthenticated state-changing endpoints: enumerate all routes (python manage.py show_urls or the router list) and check every non-AllowAny ViewSet for permission_classes and throttling on public endpoints.
  4. Check commit history for removed files that previously contained secrets (a common source of residual backdoors).
  5. Confirm production docker-compose does not publish DB/Redis ports and runs containers as non-root with cap_drop: ALL.
  6. Verify server-side commands (ensure_admin, health checks) are not reachable via HTTP.
  7. Run dependency scans (pip-audit, npm audit) to rule out a compromised dependency acting as a supply-chain backdoor.
  8. Review the NID Access Log daily during the first weeks of integration — unexpected reads of specific NIDs would indicate misuse.
Conclusion: A systematic review of the current codebase found no developer-side backdoor. The only residual items are deployment-discipline matters (changing default credentials, using the hardened production compose, and optionally migrating tokens to HttpOnly cookies). These are standard go-live controls and can be closed before the NID API integration goes live.
