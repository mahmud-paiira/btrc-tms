1. System Overview & Architecture

The BRTC Training Management System (BRTC TMS) is a full-stack web platform that administers the entire training lifecycle — from public circulars and NID-verified applications through batch enrollment, attendance, assessment, certification, job placement and finance/allowance management. It is built as a modern single-page application (SPA) backed by a RESTful API, with asynchronous background processing and a containerised deployment model.

Figure 1: End-to-end architecture (“Client → Edge → Application → Data” pipeline with async workers and the document pipeline).

Core design principles

  • Separation of concerns — frontend SPA, REST API, background workers, and reverse proxy are independent, containerised components.
  • Stateless API authentication via JWT so the same backend serves the web application and future integrations.
  • Asynchronous by default — slow work (reports, certificates, notifications) is delegated to Celery instead of blocking request threads.
  • Modular domain design — the backend is split into 17 Django apps mirroring business areas (accounts, applications, batches, assessments, certificates, finance, etc.).

3. Backend Technology & API

Production hardening includes resource limits (CPU/memory), cap_drop: ALL, read_only: true root filesystems, image pinning, Docker healthchecks on all stateful services, and bounded JSON-file logging with rotation.

Why this deployment model

  • Reproducibility — identical environments from local laptops to the production server.
  • Isolation — each component is a separate process; workers can scale independently under load.
  • Least privilege — read-only filesystems, dropped capabilities and non-root users reduce the blast radius of a compromise.

7. Security Architecture

Security is applied in layers — network/edge (Nginx), application (Django/DRF), and client (React). Every layer is described below.

7.1 Transport & edge security (Nginx)

  • TLS only — port 80 redirects to HTTPS; TLS 1.2/1.3 enforced, weak ciphers (!aNULL:!MD5:!3DES:!RC4) excluded, session cache configured.
  • HSTS — Strict-Transport-Security: max-age=31536000; includeSubDomains; preload.
  • Security headers — X-Frame-Options: SAMEORIGIN, X-Content-Type-Options: nosniff, Referrer-Policy, Permissions-Policy (camera/mic/geolocation blocked), and a strict Content-Security-Policy (scripts only from self; frame-ancestors self).
  • Fingerprint reduction — server_tokens off hides the Nginx version.
  • Rate limiting — per-IP zones per endpoint class: login/OTP 10 r/m, admin 10 r/m, public API 15–20 r/m, general API 30 r/m, all with burst allowances and a 429 response.
  • Upload cap — client_max_body_size 20M prevents oversized payloads.
  • Docs disabled — /swagger/ and /redoc/ return 404 in production.
  • Health endpoint restricted — only reachable from loopback/private ranges.

7.2 Application-layer security (Django / DRF)

  • JWT authentication — Bearer access tokens (2-hour lifetime), refresh token rotation with blacklisting of old tokens (7-day refresh lifetime).
  • Default deny — DRF default permission is IsAuthenticated; public endpoints are explicit exceptions.
  • Throttling — per-user (1000/hour) and anonymous (100/hour) DRF throttles complement the Nginx rate limits.
  • Production hardening block — automatically enforced when DJANGO_DEBUG=False: HSTS, SECURE_CONTENT_TYPE_NOSNIFF, secure/HTTP-only session and CSRF cookies, and SECURE_PROXY_SSL_HEADER for correct schema detection behind Nginx.
  • Secrets & configuration — DJANGO_SECRET_KEY, DB password and Redis password come from the environment (.env), never committed; Redis uses --requirepass in production.
  • Audit trail — django-simple-history records every model change; NID lookups are logged (NIDAccessLog) for accountability.
  • Verified identity — public registration verifies phone via OTP and validates NID through the national NID API before applications are accepted.
  • CSRF/XSS defaults — Django CSRF middleware active; security middleware enables X-Content-Type-Options and browser-XSS protection at the application layer as well.

7.3 Client-side security (React)

  • All user-generated and rich-text content is sanitised with DOMPurify before rendering (defence-in-depth against XSS).
  • Tokens are held in memory/session state and sent only via the Authorization header through Axios interceptors; no secrets are embedded in the bundle.
  • The strict CSP header also restricts script sources to self, containing any client-side injection.
Operational notes: TLS certificates are mounted read-only into Nginx (/etc/nginx/ssl); the database port is not exposed to the public internet; the frontend runs as a non-root user; and deployments pin versions of every base image for supply-chain stability.

In short, the stack was chosen for maturity, security and maintainability:
